# HDR codec source and verification

`src/core/hdr-codecs.ts` is a portable TypeScript codec; it adds no native or WASM runtime dependency. Its raster is `Float32Array` premultiplied **encoded extended sRGB**, with finite signed colors, alpha in `[0, 1]`, and white at 1. RGB can exceed alpha or white. File samples are never substituted with a display PNG.

## OpenEXR

The codec implements single-part flat scanline RGB/RGBA, HALF/FLOAT channels, and NONE/RLE/ZIPS/ZIP compression. HALF uses IEEE binary16 round-to-nearest-even. ZIP's byte rearrangement and predictor, RLE packet decoding and chunk layout were checked against the [official OpenEXR file layout](https://openexr.com/en/latest/OpenEXRFileLayout.html), [Zip implementation](https://github.com/AcademySoftwareFoundation/openexr/blob/main/src/lib/OpenEXR/ImfZip.cpp), and [RLE implementation](https://github.com/AcademySoftwareFoundation/openexr/blob/main/src/lib/OpenEXRCore/internal_rle.c).

OpenEXR's RGB channels are scene-linear and conventionally premultiplied; its alpha is opacity. Import divides color by alpha before applying the extended sRGB transfer and multiplies by alpha afterwards. Export performs the inverse transfer and premultiplication, writing linear RGB and standard Rec.709/D65 chromaticities. Missing chromaticities use OpenEXR's conventional Rec.709/D65 interpretation. Explicit valid primary chromaticities are converted through XYZ and Bradford white adaptation. A `colorInteropID` or ACES container flag is refused until its interpretation is implemented. These are actual color transformations, not a metadata relabel.

The [official alpha convention](https://openexr.com/en/latest/TechnicalIntroduction.html#premultiplied-vs-un-premultiplied-color-channels) permits nonzero emissive RGB at alpha zero. This editor's encoded premultiplied raster cannot preserve those samples through unpremultiplication, so the codec explicitly refuses them. It also refuses multipart, tiled, deep, layered/subsampled channels, UINT channels, unequal display/data windows, non-square pixels, and PIZ/PXR24/B44/DWA/HTJ2K compression. This is a defined initial EXR subset, not complete OpenEXR compatibility.

`inspectEXR` checks headers, dimensions and the working allocation estimate before returning data for decoding. Its estimate includes original bytes, the Float32 output, temporary packed/raw buffers, offset bookkeeping and a zlib allowance. Decoding bounds decompression output and checks chunk positions, unique scanlines and overlapping chunks. Nonfinite color/alpha samples and colors beyond the editor's supported finite range are rejected. The default cap is 512 MiB and 32 MP; callers can lower it.

`encodeEXR(width, height, hdr, options)` supports explicit `pixelType: 'half' | 'float'` and `compression: 'none' | 'rle' | 'zips' | 'zip'`. HALF is a lossy sample representation. HALF linear overflow and alpha underflow that would create an unsupported emissive pixel are explicitly refused. New full-precision assets should request FLOAT, while existing loaded EXR source bytes should remain untouched until an actual edit. No claim is made that encoded half bits stay identical after nonlinear transfer and back.

## Radiance RGBE

`decodeRadianceHDR` accepts flat, old repeated-pixel packets, and modern per-channel RLE; both axis orders and their signs are honored. It reverses recorded EXPOSURE/COLORCORR and converts specified PRIMARIES to sRGB D65. With no PRIMARIES it uses Radiance's standard RGB primaries and equal-energy white, then adapts to D65. It follows the [official Radiance color implementation](https://github.com/LBNL-ETA/Radiance/blob/master/src/common/color.c), including the half-step reconstructed RGBE mantissa. XYZE and extra concatenated frames are explicitly refused.

`encodeRadianceHDR` writes standard sRGB PRIMARIES and RGBE/RLE. RGBE cannot carry alpha or signed colors, so encoding requires an opaque, nonnegative source. Use OpenEXR for transparent or signed HDR. RGBE quantization is inherent in the format and is not a float-preserving alternative to EXR.

## Independent references and current gate

`scripts/generate-hdr-codec-reference.py` uses the system OpenCV 4.13.0 build's upstream OpenEXR codec, independently of this TypeScript implementation. It creates ten HALF/FLOAT, RGB/RGBA and four-compression fixtures under `fixtures/hdr-codec`, including two ZIP chunks, negative colors, very low alpha and highlights above white. The reference records actual decoded linear samples, producer version and SHA256s. Source tests reconstruct expected encoded samples using a separately expressed transfer formula.

`npx tsx --test tests/hdr-codecs.test.ts` currently passes all eight tests, covering those ten fixtures, structural refusals, budgets, HALF ties/subnormals, low-alpha round trips, shifted/reordered chunks, Radiance RLE/orientation/exposure/primaries and source immutability. A separate manual verification decoded all eight product-generated HALF/FLOAT × NONE/RLE/ZIPS/ZIP outputs with OpenCV's OpenEXR codec. Their scene-linear samples exactly matched independently transformed and appropriately half/float-rounded expected values (maximum delta 0). That runtime evidence is in ignored `test-results/hdr-codec/independent-encode-verification.json`; it is not checked-in fixture data.

## Project assets and standalone import

Version 13 project image layers accept canonical UUID `.exr` filenames; masks remain PNG8 gray. `makeAssetEXR` preserves the complete original encoded source and hash, alongside independent Float32 working pixels and a clipped PNG8 display proxy. A sub-white EXR remains HDR-capable until explicit depth conversion. This intentionally differs from upstream's peak-based import classification to preserve the source container and precision. Existing EXR is copied unchanged on metadata-only save. New edited HDR assets use FLOAT+ZIP. Mixed EXR/PNG16 projects save as v13; projects without HDR fall back to v12 or v11 according to referenced assets. Byte budgets include retained Float32, Uint16, canonical encoded and display backing stores, with shared immutable buffers counted once.

FLOAT+ZIP stores scene-linear samples, while editing uses encoded extended sRGB. Reopening an edited file performs the transfer again and can round the Float32 working values. A 4096-pixel signed/highlight/low-alpha fixture changed 553 of 16384 working samples, with a maximum one Float32 ULP and absolute delta 3.725290298461914e-9; alpha and the original input array were unchanged. This is a measured fixture result, not a universal precision bound. Encoded source bytes remain byte-identical through project saving; decoded working arrays are not promised bit-identical after edited-file reopen. See `tests/hdr-review.test.ts` and ignored `test-results/hdr-codec/float-transfer-roundtrip.json` for current measurements.

`prepareWideImport` is called before the ordinary importer: EXR preserves original bytes; PNG16 preserves original PNG samples/bytes; Radiance and floating TIFF are color-converted and persisted as FLOAT+ZIP EXR. Ordinary integer images stay on the existing importer route. The original RGBE/TIFF container is not the persisted project asset; import warnings state this boundary explicitly.

## Floating TIFF

`hdr-tiff.ts` separately handles classic TIFF, first image, stripped RGB/RGBA IEEE half/float/double, chunky/planar storage, both byte orders, NONE/LZW/Deflate, floating predictor 3, and all eight orientations. Alpha association is honored before transfer conversion. Float64 samples are rounded once into the Float32 working representation and this is disclosed. Untagged floating TIFF is interpreted as scene-linear Rec.709/D65 with a warning. Linear RGB matrix ICC profiles are converted through their declared primaries without gamut clipping; nonlinear/LUT profiles and separate transfer/colorimetry declarations require explicit conversion. Tiled/BigTIFF and non-RGB formats are explicitly refused. It uses the [libtiff floating predictor implementation](https://gitlab.com/libtiff/libtiff/-/blob/6aec9314ee9fe62adf464952967b611054672754/libtiff/tif_predict.c) as the byte-predictor reference; no libtiff product dependency is added.

`generate-hdr-tiff-reference.py` runs in an isolated reference Python environment and uses tifffile 2026.9.20/imagecodecs 2026.10.10, independently of the product decoder. Thirty-six fixtures cover HALF/FLOAT/DOUBLE, endian/planar/strip codec combinations; the reference records actual independently decoded samples and SHA256. Each decoded Float32 output sample exactly matches the independently expressed extended-sRGB transfer and premultiplication. Additional tests exercise associated alpha, every orientation, linear/nonlinear ICC and malformed/range/codec refusals. These source and persistence tests do not establish EXR composite/export UI, Windows runtime or HDR/EDR hardware display completion. Those gates follow integration.
